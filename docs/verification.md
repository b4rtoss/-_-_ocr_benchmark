# Проверка работоспособности

Техническую проверку проекта я провожу с помощью Codex в среде Windows 10 Домашняя x64 (сборка 19045), Python 3.12, Intel Core i5-12450H (8 ядер, 12 потоков), 16 ГБ RAM и NVIDIA GeForce RTX 4050 Laptop GPU с 6 ГБ выделенной видеопамяти. В этом отчёте фиксирую проверки запуска и обработки ошибок. Исследовательские метрики привожу отдельно в [результатах экспериментов](experiment-results.md).

## Исправления

- Убраны абсолютные пути старого рабочего окружения. Общие пути находятся в `benchmark_paths.py`; поддерживаются `OCR_BENCHMARK_DIR` и `MANGA109_ROOT`.
- Выборка для ChatGPT принимает столбец `text` из подготовленного датасета, а также `ground_truth`. Размер выборки и seed доступны в командной строке.
- Три базовых runner используют единый CSV и параметры командной строки. PaddleOCR по умолчанию работает на CPU. Модели загружаются до замера вызовов. Ошибки и отсутствующие изображения сохраняются в CSV; продолжение проверяет эталоны и не создаёт дубликаты.
- Отчёт показывает ошибки, исключает их из среднего времени, отклоняет пустые/повторяющиеся примеры и разные выборки.
- Manga Reader сохраняет успешный OCR при сбое последующего анализа Ollama. Исправлены импорт как модуля, очистка прогресса, предпросмотр повреждённого файла и защита очистки во время работы.
- Зафиксированы прямые зависимости; добавлен GitHub Actions с тестами Windows/Linux.

## Выполненные проверки

- Установка приложения и базового бенчмарка в новом окружении Python 3.12; `pip check` проходит.
- 13 тестов: подготовка кропов и выборки, продолжение с ошибками, CER/NFKC, проверка одинаковых выборок, экспорт отчёта, справка CLI, порядок страниц, сбои OCR/Ollama.
- Все Python-файлы разобраны синтаксическим анализатором.
- Tkinter: создание окна, добавление и предпросмотр изображения, экспорт JSON/TXT, очистка данных.
- Из `Hamlet/008.jpg` с его XML-разметкой получено 11 реальных кропов. Первые три обработаны всеми тремя OCR-системами без ошибок вызова. Для PaddleOCR также проверено продолжение после прерывания.
- Полный вызов `Analyzer.analyze` на реальном кропе: 3 области OCR, непустой анализ Ollama, без предупреждений, около 50 с.
- Ollama `qwen3-vl:4b-instruct`: успешный текстовый запрос и запрос с изображением страницы. Это подтверждает работу API, а не достоверность описания.

Диагностический отчёт на одинаковых трёх кропах:

| Система | Примеры | Ошибки вызова | CER | Среднее время вызова |
| --- | ---: | ---: | ---: | ---: |
| Manga OCR | 3 | 0 | 0.0588 | 0.77 с |
| Tesseract | 3 | 0 | 1.0000 | 0.50 с |
| PaddleOCR CPU | 3 | 0 | 0.2549 | 30.69 с |

Трёх примеров недостаточно для оценки качества модели. Время включает предварительную обработку конкретного OCR, но не первоначальную загрузку модели; возможны внутренние разовые расходы движка.

## Ограничения проверки

При технической проверке я ограничиваюсь автоматическими тестами и короткими пробными запусками. Полный бенчмарк, запуск MangaLMM с 4-битной квантизацией, обработка полной страницы PaddleOCR и отдельные языковые модели английского/русского заново не прогоняются. Для MangaLMM проверены синтаксис скриптов и согласованность путей. Ранее полученные результаты на 3116 кропах, сравнение на 50 кропах и эксперимент MangaLMM на 50 страницах я описываю в [отчёте об исследовании](experiment-results.md).

В старом стороннем GPU-окружении PaddlePaddle обнаружен `WinError 127` при загрузке cuDNN. Это окружение не изменялось; штатная установка приложения использует CPU. PaddlePaddle 3.3.1 с oneDNN выдаёт `ConvertPirAttribute2RuntimeAttribute` на этой Windows-системе, поэтому oneDNN отключён только на Windows. Без него распознавание работает, но один кроп занял более минуты. Полные страницы могут обрабатываться существенно дольше. Остановка очереди происходит после текущего вызова.

Команда проверки без загрузки OCR-моделей:

```powershell
python -m unittest discover -s tests -v
```
